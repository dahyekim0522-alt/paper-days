# 구현 결정과 검증 범위

## 페이지 넘김

2026-11-05 npm 메타데이터 및 배포 소스를 조사했다.

| 후보 | 확인된 배포 버전 | 판단 |
| --- | --- | --- |
| StPageFlip / page-flip | 2.0.7 (npm 메타데이터 수정 2022년) | DOM 페이지·그림자·portrait 지원. 직접 연결 |
| react-pageflip | 2.0.3 (npm 메타데이터 수정 2022년) | 같은 엔진의 래퍼. React 19에서 오래된 래퍼에 의존하지 않기로 함 |

유지관리되는 호환 포크의 안정성을 별도로 확인하지 못했다. `page-flip`을 2.0.7로 고정하고 사용 범위를 어댑터로 제한했다. 런타임 패키지에 TypeScript 선언이 없어 사용 API에 한정한 선언을 작성했다.

확인 및 보완한 상위 라이브러리 문제:

- portrait에서 `disableFlipByClick`가 역방향 프로그램 이동을 막는 것을 브라우저 테스트로 재현했다. 해당 옵션을 끄고 편집 화면을 책 밖의 dialog로 분리했다.
- native touch folding에서 역방향이 잘못 추론되는 현상을 재현했다. capture 단계에서 터치의 수평 이동을 감지해 명시적인 next/prev 애니메이션을 실행한다. 모바일은 스와이프 종료 후 종이 말림 애니메이션이 실행되며, 손가락을 실시간으로 따라 구부리는 동작은 제공하지 않는다. 마우스는 기본 모서리 드래그를 사용한다.
- `destroy()`가 렌더 루프를 중단하지 않는 배포 소스를 확인했다. 초기화 및 해당 콜백 실행 중에만 requestAnimationFrame을 추적하는 animationScope로 각 인스턴스의 예약 프레임을 정리한다. 전역 함수를 지속 교체하지 않는다.
- 모션 감소 설정에서는 버튼/키보드/스와이프를 즉시 페이지 이동으로 처리하고 마우스 애니메이션 입력을 차단한다. 설정 변경도 감지한다.

날짜당 본문/사진 2페이지, 전날/해당 날/다음 날 총 6페이지만 렌더한다. 기록 개수와 무관하게 페이지 수를 제한한다. 다른 날짜로 넘어간 애니메이션이 끝난 다음 날짜 창을 다시 구성한다. 모바일에서는 하루에 2장을 넘겨 다음 날로 이동한다.

## 저장과 복원

- 하루 한 기록은 IndexedDB의 `&date` 고유 인덱스와 저장 트랜잭션으로 강제한다.
- 800ms debounce 자동 저장. 본문 임시 캐시는 localStorage, 사진을 포함한 초안은 IndexedDB에 보관한다. 닫기는 저장을 기다리고 실패하면 창을 유지한다. 브라우저 종료는 미저장 변경 경고를 제공한다.
- 편집 취소는 확인 후 편집 전의 일기/사진 상태를 복원한다. 편집 도중 날짜를 바꾸면 기존 날짜를 저장한 후 이동한다.
- 강제 프로세스 종료, IndexedDB와 localStorage 모두 사용 불가, 저장 완료 전 기기 종료까지 완전한 보존을 보장하지는 않는다. 실패 메시지를 확인하고 백업해야 한다.
- 사진은 JPG/PNG/WebP, 장당 원본 20MB 이하, 최대 8장. 긴 변 1600px 이하 WebP(품질 .85)로 변환한다. 원본 바이트를 보존하는 기능은 없다.
- JSON 백업은 버전/날짜/중복/감정/사진 연결/base64를 검사한다. 파일 최대 150MB. Dexie export/import 플러그인 대신 작은 버전 명시 포맷을 사용해 Blob을 data URL로 직렬화한다.
- 복원은 확인 후 **전체 교체**한다. 날짜별 병합을 하지 않으므로 중복 기록이 없다. 사진 디코딩/base64 변환 후 단일 트랜잭션으로 교체해 DB 실패 시 롤백한다. 복원 전 사용자가 현재 데이터를 백업하도록 안내한다.

## 남은 검증과 제한

- Chromium 자동화 검증이며 실제 iOS Safari/Android 기기 검증은 하지 않았다. 모바일 CDP 터치 이벤트와 viewport 회전으로 테스트했다.
- Windows에서 직접 실행하지 않았다. npm 스크립트는 플랫폼 독립 명령이며 OS별 경로가 필요하지 않다.
- 외부 서버·동기화·로그인·사진 자유 배치·테마는 구현 범위에 포함하지 않았다.
- 검색/달력은 일기 텍스트 메타데이터를 메모리에 읽는다. 사진은 주변 3일만 읽는다. 수만 건 기록에 대한 성능 부하 검증은 하지 않았다.
- 백업은 메모리에서 JSON과 base64를 만들므로 대규모 사진 보관에는 적합하지 않다. 비공개 모드나 브라우저 저장소 정리로 데이터가 사라질 수 있다.
- GitHub Pages 워크플로 파일을 제공했으나 원격 배포는 실행하지 않았다.


## 1.1.0 설치형 앱(PWA)

- vite-plugin-pwa 2.0.0의 injectManifest와 Workbox 7.4.1 사용. 생성된 manifest는 상대 start_url/scope를 사용해 GitHub Pages의 `/paper-days/` 하위 경로를 지원한다. 일반/마스커블 PNG 아이콘과 iOS apple-touch-icon을 제공한다.
- 빌드 산출물과 자체 호스팅 폰트를 설치 시 precache한다(약 12MB). 최초 캐시 설치 성공 후 오프라인을 지원한다. 원격 API 응답이나 일기·사진을 서비스워커 캐시에 넣지 않는다. IndexedDB 저장은 그대로 유지한다.
- 서비스워커는 개발 서버에서는 비활성화된다. production 빌드로 실제 HTTP 캐시를 지운 뒤에도 오프라인 새 창에서 다시 여는 것을 검증한다.
- 새 worker는 waiting 상태에서 대기한다. 명시적 업데이트를 요청할 때 모든 같은 scope 창에 MessageChannel로 확인해 열린 dialog가 있거나 응답이 없으면 활성화를 거부한다. 현재 창만 활성화 성공 후 새로고침하며 다른 창은 자동 새로고침하지 않는다. 모든 창을 닫았다 다시 열면 브라우저의 정상 worker 활성화 절차를 따른다.
- 설치 UI는 Chromium의 beforeinstallprompt 이벤트를 사용하며 iOS는 Safari 공유 메뉴 안내를 제공한다. 자동 설치·앱스토어 등록·기기 간 동기화는 하지 않는다. iOS는 설치 전후 저장소가 분리될 수 있어 백업/복원을 안내한다.
- GitHub API와 실제 GitHub Pages 도메인은 현재 실행 환경의 네트워크 정책에서 차단되었다. Git push는 가능하지만 이 사실이 Pages 관리 권한이나 배포 성공을 보장하지 않는다. 실제 배포 성공은 GitHub Actions/Pages에서 별도 확인해야 한다.
